Do you really master LRU?

Every cache is a bet that you’ll want the same thing twice. Since caches are finite, every cache also needs an answer to an awkward question: when it’s full and something new arrives, what gets thrown out?

LRU is the most common answer. It’s also the answer that almost no production system implements literally. That gap is the interesting part.

1. What is LRU?

LRU stands for Least Recently Used. When the cache is full, evict whatever hasn’t been touched for the longest time.

The policy rests on one assumption: temporal locality. If something was accessed recently, it’ll probably be accessed again soon. This holds remarkably well for a lot of real workloads: web sessions, database pages, file blocks, CPU memory access.

It’s worth seeing where LRU sits among the alternatives:

Policy Evicts Trade-off
FIFO Oldest inserted Trivially cheap. Ignores usage entirely.
LRU Oldest accessed Good default. Costs bookkeeping on every read.
LFU Least frequently accessed Better for stable hot sets. Slow to forget old favourites.
Random Anything Nearly free, surprisingly hard to beat by much.
Belady’s OPT The item used furthest in the future Optimal, and impossible: it requires clairvoyance. Used as a benchmark.

LRU wins as a default because it’s the cheapest policy that actually pays attention to what your program is doing.

2. Put it simply

Imagine your desk has room for exactly five sheets of paper.

You work through them all day. Each time you need a sheet, you pull it out, read it, and put it back on top of the pile. Sheets you use constantly keep floating to the top. Sheets you haven’t touched since morning sink toward the bottom.

Now a sixth sheet arrives and there’s no room. Which one do you get rid of? The one at the bottom, the one you haven’t touched the longest.

That’s LRU. The whole policy.

The subtlety is in how you maintain the pile. If you just dumped all five sheets in a heap and wrote the time on each one, finding the oldest would mean checking all five every single time. Fine for five sheets. Terrible for five million.

The trick that makes LRU practical is that you keep the pile sorted as you go, incrementally. Every access does one tiny bit of reordering work, so eviction is instant: just grab the bottom.

Which leads to the thing that makes LRU expensive in ways people don’t expect: every read is also a write. Reading from an LRU cache mutates it, because reading changes the order. Hold that thought. It’s why section 4 exists.

3. Implementations

The naive version

Store a timestamp with each entry. To evict, scan everything and drop the oldest.

Reads are O(1), evictions are O(n). For a small cache this is genuinely fine, and its simplicity has real value. For anything large it falls over.

The classic: hash map + doubly linked list

This is the canonical O(1) solution, and the one interviewers are fishing for.

Two structures working together:

  • A doubly linked list holds entries in access order. Most recent at the head, least recent at the tail.
  • A hash map maps each key directly to its node in that list.

The hash map gives you O(1) lookup. The linked list gives you O(1) reordering. Neither works alone:

  • A list alone means scanning to find a key: O(n).
  • A hash map alone has no notion of order.

The list must be doubly linked. To unlink a node in O(1) you need its predecessor, and only a backward pointer gives you that for free.

Both get and put are O(1). Memory cost is the payload plus two pointers per entry: 16 bytes on a 64-bit machine, which sounds trivial until you’re caching a hundred million small keys.

The sentinel head and tail nodes are worth noting. Without them, every unlink and insert needs null checks for “is this the only node,” “is this the first node,” and so on. With them, the list is never actually empty and the code has no branches.

The three-line version

Most languages ship this already. Java’s LinkedHashMap has an access-order mode built in:

Python’s functools.lru_cache decorator does it for function memoisation, and collections.OrderedDict exposes move_to_end() if you want to build it yourself. Go has container/list, and the community standard is hashicorp/golang-lru. C++ pairs std::list with std::unordered_map.

Reach for these first. Write the manual version when you need to customise eviction, or when someone’s asking you to on a whiteboard.

Where the textbook version breaks: concurrency

Here’s the practical problem. Since every read mutates the linked list, every read needs a write lock. A cache is usually read-heavy (that’s the entire point of a cache), so you’ve built a structure whose hot path is a global mutex. It becomes the bottleneck immediately under concurrent load.

Real systems escape this three ways:

  1. Shard it. Split into N independent caches keyed by hash. Contention drops roughly N-fold. Eviction is now per-shard rather than global, so it’s no longer true LRU, but it’s close enough and it’s the simplest fix that works.
  2. Buffer the accesses. Record reads into per-thread ring buffers and replay them onto the list later, in batches. Reads become lock-free. This is what Caffeine does.
  3. Stop tracking exact order. Approximate it with a bit or a coarse timestamp per entry. This is what almost every large system actually does, which brings us to the next section.

4. How real systems bend LRU

Textbook LRU has three problems at scale: the memory overhead of the pointers, the lock contention above, and one more that’s easy to miss.

Scan resistance. Suppose your cache is holding a nicely warmed hot set, and then some batch job does a single full-table scan. Every page in that scan is “recently used,” so LRU dutifully evicts your entire hot set in favour of data that will never be read again. One nightly report can destroy a cache’s hit rate. Pure LRU has no defence against this at all, because it can’t distinguish “used once, just now” from “used constantly.”

Here’s how different systems respond.

Redis: sample, don’t sort

Redis doesn’t maintain a global LRU list. Doing so would cost two pointers per object. For a server holding hundreds of millions of small keys, that overhead is unacceptable.

Instead, each object header carries a 24-bit clock timestamp, updated on access. When memory is tight, Redis picks a few random keys (maxmemory-samples, default 5), compares their timestamps, and evicts the oldest of the sample.

That’s it. It’s LRU by opinion poll. With 5 samples the result is a decent approximation of true LRU; raising the value gets closer at higher CPU cost. Redis 3.0 improved the accuracy by keeping a pool of the best eviction candidates seen so far, carried across rounds, so good candidates aren’t forgotten between samples.

Redis 4.0 later added LFU mode (allkeys-lfu), using an 8-bit logarithmic counter with time-based decay. The motivation is precisely the scan problem: with LRU, a key touched once ranks equal to a key touched ten thousand times.

Linux kernel: two lists, then many

The page cache uses a two-list strategy: an active list and an inactive list.

New pages land on the inactive list. They only get promoted to active on a second reference. Eviction pressure falls on the inactive list first.

This is scan resistance, cheaply achieved. A sequential read touches each page once, so those pages cycle through the inactive list and get reclaimed without ever displacing the genuinely hot pages on the active list. Ordering within lists is approximated with a referenced bit (CLOCK-style) rather than tracked exactly.

Linux 6.1 merged MGLRU (Multi-Generational LRU), which generalises two lists into multiple generations. Pages age through generations, and eviction targets the oldest. It reduced reclaim overhead substantially and improved hit rates under memory pressure.

MySQL InnoDB: insert in the middle

InnoDB’s buffer pool splits its LRU list into a “young” sublist and an “old” sublist, with new pages inserted at the boundary, about 3/8 of the way from the tail, not at the head.

There’s a second guard: innodb_old_blocks_time (default 1000ms). A page must survive in the old sublist for at least that long and be accessed again before it’s promoted to young.

Both mechanisms exist for the same reason. A full table scan reads each page once, in quick succession. Under textbook LRU it would flush the buffer pool. Under midpoint insertion, those pages never make it out of the old sublist.

CPU caches: pseudo-LRU

True LRU in hardware needs enough state to order every line in a set, which is impractical beyond low associativity. Processors use tree-PLRU instead, a binary tree of direction bits needing only n−1 bits per set. It points at an old line rather than the oldest. In silicon, close enough at a fraction of the cost is the right trade.

Caffeine: admission control

The most interesting modern variant. W-TinyLFU asks a different question: not “what should I evict?” but “should I admit this at all?“

A compact Count-Min Sketch tracks approximate access frequencies across a much larger key space than the cache itself holds. When a new item arrives and something must be evicted, the candidate is compared against the eviction victim, and the new item is only admitted if it’s more frequent. A small LRU window in front handles items that are genuinely new rather than genuinely unpopular.

The result is that a scan can’t pollute the cache: scanned items simply never earn admission. Caffeine consistently beats LRU on real-world traces, often substantially.

Worth also knowing: ARC (Adaptive Replacement Cache) balances recency and frequency using “ghost” lists of recently evicted keys, adapting its split automatically. ZFS uses it. PostgreSQL famously backed away from it over patent concerns and uses a clock-sweep algorithm instead.

5. Wrapping up

LRU is the right default. It’s simple, it matches how programs actually behave, and the hash map plus doubly linked list gives you O(1) on everything.

But notice what happened every time we looked at a real system. Nobody implements the textbook version, and they all deviate in the same three directions:

  • Approximate the ordering. Redis samples, Linux uses reference bits, CPUs use a bit tree. Exact recency ordering is rarely worth what it costs.
  • Segment the cache. Linux’s active/inactive lists, InnoDB’s young/old sublists, Caffeine’s window. Segmentation is how you buy scan resistance.
  • Filter what gets in. W-TinyLFU’s admission policy is the sharpest version of this, and the biggest departure from LRU thinking.

Those three moves are the actual lesson. LRU is one point in a design space defined by memory overhead, lock contention, and how badly a sequential scan can hurt you. Knowing where your workload sits on those axes matters more than knowing the data structure.

And if you’re preparing for interviews: implement the linked list version until it’s automatic, then be ready to explain why the read path needs a write lock. That second question is where the conversation gets interesting.
