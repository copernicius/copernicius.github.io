A quick look at consistent hashing

Picture this. Your app is doing great. Traffic keeps climbing, so you do the sensible thing and grow your cache cluster from 10 servers to 11.
One extra machine. That should be harmless.

Then the dashboards go red. Cache hit rate falls off a cliff, basically to zero. Millions of queries that used to be served from memory now slam straight into your database. The database buckles, and the whole system goes dark.

What happened? You just triggered a cache avalanche. And the thing that caused it is the very first tool most of us reach for when we split data across servers: modulo hashing.

Here is the story of how a simple bit of arithmetic falls apart at scale, and how a group of MIT researchers fixed it with an idea that still runs under half the internet today.

The late 90s, and a world full of avalanches

Rewind to the late 1990s. The web was having its first real growth burst. A single server could no longer keep up, so distributed caching became the default: spread your key-value pairs across a group of servers, and let the client figure out which server holds what.

It is beautifully simple. The distribution is even, it costs almost nothing to compute, and as long as N never changes, it just works.

But out in the real world, server fleets are never still. Machines crash. New ones get added. Maintenance happens. And modulo hashing has one fatal flaw: the moment N changes, almost every key maps to a different machine.

Why modulo hashing fails so badly

The reason is right there in the math.

Say you have 10 servers and you scale up to 11. Roughly 90 percent of your keys now land on a different server than before.

This is not a bug in your code. It is just arithmetic. The denominator N is baked into every single lookup, so when N moves, it drags almost the entire keyspace with it. One small change, and your cache is effectively empty overnight.

People tried to work around it. Over-provision servers so you rarely scale. Double the cluster size in one go to limit the shuffle. Re-index during the quiet hours. All of these are band-aids. None of them touch the real problem, which is that the server count and the data mapping are welded together.

A young company called Akamai ran straight into this wall while trying to solve content delivery. So they took the problem to some theoretical computer science researchers at MIT.

The breakthrough: put keys and servers on a ring

In 1997, a team at MIT published a paper called Consistent Hashing and Random Trees.

Their key insight was almost cheeky: stop using N in the lookup at all.

Instead, take both your servers and your keys and map them onto the same fixed-size ring, usually the range from 0 to 2^32 minus 1. Imagine a giant clock face.

Here is the whole trick in three steps:

  1. Hash each server’s identifier (its IP, for example) and drop it onto the ring.
  2. Hash each key with the same function so it lands somewhere on the ring too.
  3. To find a key, start at its spot and walk clockwise until you hit the first server. That server owns the key.

Why this is such a big deal

When you add or remove a server, the only keys that move are the ones sitting between the new server and the one before it on the ring. Everything else stays exactly where it was.

The math backs this up. With N servers, adding one more only disturbs about one Nth of your keys.

  • In a 10 node cluster, adding a node moves about 10 percent of keys, versus 90 percent with modulo.
  • In a 100 node cluster, adding a node moves about 1 percent.

Notice the direction of that trend. The bigger your cluster gets, the less a scaling operation hurts. That is the opposite of how modulo behaves, and it is the whole point.

Fixing uneven load with virtual nodes

The basic ring has one weakness. If your hash function happens to place a few servers close together, one unlucky server can end up owning a huge arc of the ring, and it takes on way more load than the rest.

The paper’s fix is virtual nodes.

Instead of giving each physical server one point on the ring, you give it many virtual identities, say server1-1, server1-2, server1-3, and so on.

Scatter those virtual nodes all over the ring, and the load evens out across your fleet. It is a classic systems move: use lots of small random samples to get a smooth, balanced result.

What it looks like under the hood

You do not need much code to see how this works. Finding a key on the ring is really just a ceiling search: given the key’s hash, find the smallest node hash that is greater than or equal to it. If you run off the end, wrap back to the first node.

The Redis twist: hash slots

It is worth seeing how a modern tool adapted the idea. Redis Cluster does not use a continuous ring at all. It uses 16,384 fixed hash slots.

Keys are hashed with hash(key) % 16384 to pick a slot, and slots are explicitly assigned to nodes. You can think of this as a pragmatic, simplified consistent hashing: a fixed, bounded lookup space, with slot migration that is easy for an operations team to reason about and move around by hand.

The system design lessons underneath

Consistent hashing is more than a caching trick. It quietly demonstrates a few principles worth carrying into other designs:

  1. Keep volatile state off the hot path. The current node count changes all the time, so do not bake it into every lookup.
  2. Make change cheap. The cost of a change should scale with the size of the change, not the size of the whole system.
  3. Keep the blast radius small. When something scales or fails, contain the fallout to a predictable, local slice.

Where it shows up today

The paper went from a niche academic result to a foundation of distributed infrastructure:

  • DynamoDB and Apache Cassandra use consistent hashing rings to partition data across storage nodes.
  • Memcached clients use it to spread cache entries across independent instances, with no central coordinator.
  • Akamai’s CDN still leans on these ideas to route billions of requests to edge servers.

Are there better options now?

Consistent hashing set the bar, but people never stop tuning.

  • Jump Consistent Hash (Google, 2014) is fast and needs zero memory, no stored ring, no virtual nodes. It is only a few lines of code and it flies. The catch is that it only supports adding or removing nodes at the tail end of the cluster.
  • Rendezvous hashing (also called highest random weight) scores every key-node pair and picks the highest scorer. It gets you incremental rebalancing without any ring or virtual nodes at all.

In today’s cloud-native world, a lot of traffic routing is handled higher up by service meshes and ingress controllers. But go down into the engine room, where database sharding, distributed caches, and storage partitions live, and the principle is exactly the same as it was in 1997: scaling should not break the world.
